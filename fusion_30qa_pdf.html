🏆 Competition & Problem Statement
Q1What problem does FUSION solve and why is it important for India?
Over 88% of India's 12 million+ informal trade artisans (electricians, plumbers, AC technicians) face 25–40% platform commission cuts, zero healthcare, no social security, and no grievance mechanism. Platforms like UrbanClap act as corporate middlemen keeping most of the value. FUSION eliminates the middleman with a cooperative 90/10 payout model where workers receive 90% of every booking directly and 10% builds a peer-funded Mutual Welfare Fund for medical, equipment, and training claims.
Q2How is FUSION different from existing platforms like UrbanClap or Taskrabbit?
UrbanClap charges 20–40% commissions, enforces opaque rating penalties, and provides no social security. FUSION is fundamentally different: (1) Cooperative ownership model — workers are stakeholders, not vendors. (2) Guaranteed 90% payout — no hidden deductions. (3) 100% escrow protection — customer funds locked until job completion. (4) Mutual welfare fund — healthcare, equipment grants, and skill certification reimbursements funded from the 10% platform share. No existing competitor offers all four simultaneously.
Q3What is the revenue and sustainability model of FUSION?
FUSION takes 10% of every completed booking. This 10% is split: ~6% funds the Mutual Welfare Pool (healthcare, equipment, training grants for workers) and ~4% covers operational costs (servers, hosting, development). Since the cooperative pool grows with every transaction, it becomes self-sustaining. Workers benefit more as the platform scales — making FUSION's growth directly aligned with worker welfare, unlike exploitative aggregators.
Q4Who are your target users and how did you validate the idea?
Three distinct user groups: Customers (homeowners, office managers needing trade services), Workers (electricians, plumbers, AC technicians, painters, carpenters), and Admins (cooperative committee overseeing platform fairness). Validation: field interviews with 35+ trade artisans across industrial clusters revealed universal frustration with commission cuts and zero job security — directly shaping our 90/10 model and welfare claim features.
⚙️ Technical Architecture
Q5Explain the overall architecture of FUSION.
FUSION uses a 3-tier architecture: Layer 1 — React 18 SPA (frontend, port 5173); Layer 2 — Node.js + Express REST API (backend, port 3001); Layer 3 — Supabase (PostgreSQL 15 + Auth + RLS). The frontend communicates directly with Supabase via the JS client for auth and real-time CRUD, and via HTTP fetch to the Express backend for privileged admin operations requiring the service_role key which never reaches the browser.
Q6Why did you choose Supabase over a custom PostgreSQL setup or Firebase?
Supabase provides PostgreSQL 15 (not a NoSQL like Firebase), giving us relational joins, complex queries, and ACID compliance needed for financial escrow data. Key advantages over custom PG: built-in Auth with JWT (no custom OAuth code), Row-Level Security enforced at DB level (zero data leaks even if API is bypassed), Realtime WebSocket subscriptions, and a generous free tier. Firebase lacks SQL joins, making complex booking-payment-worker queries painful.
Q7How does role-based access control work in FUSION?
Two layers: (1) Frontend routing — React Router reads profile.role from Supabase Auth session and redirects customers to /customer, workers to /worker, admins to /admin. Unauthorized routes redirect to login. (2) Database RLS policies — PostgreSQL enforces at the row level using auth.uid(). A customer querying bookings only receives rows where customer_id = auth.uid(). Even if a customer forges an API call, the database rejects unauthorized rows.
Q8How does the escrow payment system work technically?
When a customer confirms a booking, a payment record is created in the payments table with status = 'pending' and the full amount locked. The worker sees the job as CONFIRMED but payment isn't released. Only when the booking status is updated to 'completed' does a backend trigger update the payment: worker_payout = amount * 0.9 and platform_fee = amount * 0.1, with status = 'paid'. This atomic DB update prevents partial releases or race conditions.

Q&A — Frontend, UI/UX & Maps
🎨 UI/UX Design
Q9What design principles guided FUSION's UI?
Four principles: (1) Role isolation — each portal (customer/worker/admin) has its own color scheme, component library, and layout so users never see irrelevant features. (2) Glassmorphism dark mode — premium futuristic aesthetic using backdrop-blur, gradient borders, and ambient glow layers in Tailwind CSS. (3) Micro-animations — Framer Motion powers hover effects, modal transitions, and page entrances for a polished feel. (4) Progressive disclosure — complex workflows (booking → payment → tracking → review) broken into modal steps.
Q10How did you handle responsive design across devices?
Tailwind CSS utility classes with sm:, lg: responsive prefixes on all components. Layouts use CSS Grid with grid-cols-1 lg:grid-cols-12 — single column on mobile, multi-column on desktop. The navigation sidebar collapses to a bottom tab bar on small screens. Map components use 100vw width on mobile and contained panels on desktop. All font sizes use relative text-xs to text-5xl Tailwind scale.
Q11How is the booking flow designed from a UX perspective?
Five-step progressive modal flow: (1) Service Selection → browsable card grid by category. (2) Worker Selection → filtered grid showing rating, hourly rate, distance. (3) Address + Schedule → GPS map picker + date/time selector. (4) Payment Confirmation → shows escrow guarantee, 90/10 split breakdown. (5) Live Tracking → animated 5-stage progress bar with map. Each step is a separate component, reducing cognitive load and allowing the user to go back without losing progress.
Q12What UI/UX considerations were made for the Worker dashboard specifically?
Workers use the platform primarily on mobile while on the job. Key decisions: Large tap targets (minimum 44px buttons), one-tap accept/reject for job requests with clear earnings display, availability toggle prominently placed (online/offline), earnings breakdown showing exact 90% amounts (not platform's 10%), and simplified job map showing only the destination address — no confusing raw coordinates.
🗺️ Maps & Geocoding
Q13How does the GPS location and address detection work?
The geocodingService.ts module uses the browser's navigator.geolocation.getCurrentPosition() API to get GPS coordinates with user permission. These coordinates are sent to the OpenStreetMap Nominatim reverse geocoding API (nominatim.openstreetmap.org/reverse), which returns a structured JSON with house_number, road, suburb, city, state, and postcode. We parse these into a human-readable address string. Raw lat/lng is never displayed in any UI element.
Q14Why Leaflet instead of Google Maps for the map integration?
Three reasons: (1) Cost — Google Maps charges per API call. Leaflet + OpenStreetMap tiles are completely free with no API key required for standard usage. (2) Customizability — Leaflet allows full CSS/SVG control over markers, popups, and tile layers. We use Esri World Street Map light tiles for a clean Google Maps-like look. (3) Bundle size — Leaflet adds ~140KB vs Google Maps Script at ~400KB+, improving page load performance significantly.
Q15How does the worker map differ from the customer map?
Three separate map components with distinct permissions: AddressPickerMap (customer) — interactive, draggable marker, GPS button, editable address preview, saves confirmed address to Supabase. WorkerJobMap — read-only, shows only the accepted booking's job site location with address label (no marker drag, no GPS button). BookingTrackingMap (customer tracking) — shows animated stage progress, job site marker, worker location placeholder, and 5-step timeline below the map.
⚛️ Frontend Tools & Libraries
Q16Why React 18 + Vite instead of Next.js for this project?
FUSION is a role-authenticated SPA — all pages require login, so server-side rendering (Next.js's primary advantage) doesn't benefit us. Vite gives sub-millisecond HMR, ESM-native bundling, and faster cold starts than Next.js/Create React App. React 18's concurrent rendering and useTransition hooks help maintain UI responsiveness during heavy Supabase data fetches. Vite's build output is also smaller due to aggressive tree-shaking.
Q17How is form validation handled in FUSION?
React Hook Form manages form state without unnecessary re-renders (it uses uncontrolled inputs with register()). Zod defines type-safe schemas like z.object({email: z.string().email(), password: z.string().min(8)}) that run at runtime during form submission. The @hookform/resolvers/zod adapter connects them. This gives us TypeScript compile-time safety AND runtime validation with user-friendly error messages — without writing custom validation logic.

Q&A — Backend, Database & Security
🔧 Backend Tools & Express
Q18What does the Express backend do that Supabase can't handle directly?
Supabase JS client uses the user's JWT (anon or user role), so it's limited by RLS policies. The Express backend uses the service_role key which bypasses RLS entirely — needed for: (1) Admin dashboard aggregation queries across all users' data. (2) Escrow release — atomically updating payment status, worker wallet, and platform fee in one transaction. (3) Welfare claim processing — admins approving cross-user financial transfers. (4) Complex business logic like matching available workers by skill/location with load balancing.
Q19Explain the Controller-Service-Routes pattern used in the backend.
Routes (e.g., adminRoutes.ts) define HTTP endpoints and map them to controller methods — they contain no business logic. Controllers (e.g., adminController.ts) parse request params, validate the JWT role claim, call the service layer, and return HTTP responses. Services (e.g., adminService.ts) contain all business logic and Supabase queries. This separation means the service layer can be unit-tested independently of HTTP, and routes can be versioned without touching business rules.
Q20How is the backend TypeScript configured for production?
Backend uses ts-node-dev for development (TypeScript execution with live reload — no manual compilation needed). For production, tsc compiles to dist/ directory and node dist/index.js runs the compiled JS. tsconfig.json has strict: true, target: ES2020, moduleResolution: node16, and outDir: ./dist. Environment variables are typed via env.ts which validates all required keys at startup and throws a descriptive error if missing.
🗄️ Database Design
Q21How is the database schema normalized and why?
FUSION uses 3rd Normal Form normalization. Each table has a single responsibility: profiles stores identity, workers stores trade-specific data (extends profiles), bookings stores transactions (references profiles+workers+services), payments stores financial records (references bookings). No data is duplicated except necessary denormalized fields like customer_name in reviews (for display performance without joins). Foreign keys enforce referential integrity with ON DELETE CASCADE or SET NULL appropriate to each relationship.
Q22What are PostgreSQL enums used for in FUSION's schema?
Custom PostgreSQL ENUM types enforce valid status values at the database level — not just in application code. Examples: booking_status ENUM: ('requested', 'confirmed', 'dispatched', 'in_progress', 'completed', 'cancelled'). payment_status ENUM: ('pending', 'paid', 'refunded', 'failed'). user_role ENUM: ('customer', 'worker', 'admin'). This prevents invalid state transitions (e.g., a booking can't be set to 'done') even if the application code has a bug.
Q23How does Supabase Realtime work in FUSION?
Supabase Realtime uses PostgreSQL's logical replication to stream database changes over WebSocket connections. In FUSION, the customer dashboard subscribes to supabase.channel('bookings').on('postgres_changes', {table:'bookings', filter:`customer_id=eq.${userId}`}, callback). When a worker updates a booking status, the database change is instantly pushed to the customer's browser via WebSocket — updating the tracking map and status badge in real time without any polling or page refresh.
🔐 Security
Q24How is the Admin portal secured beyond just role checking?
Three layers: (1) Frontend routing guard — checks profile.role === 'admin' from Supabase session; non-admins redirected immediately. (2) RLS admin policies — PostgreSQL policies verify EXISTS (SELECT 1 FROM profiles WHERE id=auth.uid() AND role='admin') for all admin table operations. (3) Hardcoded Admin UID — the specific admin user ID (2301bb9f-c393-409a-8aca-7ae3eedc82a9) is checked server-side, so even if someone changes their role column in a non-admin account, they can't access admin functions.
Q25What happens if someone tries to bypass RLS by calling the Supabase REST API directly?
Supabase's PostgREST API requires a valid JWT in the Authorization: Bearer header for every request. The JWT is signed by Supabase with a secret key — it cannot be forged. Even with a valid JWT, the RLS policy runs on every row using auth.uid() extracted from that JWT. So a customer calling GET /rest/v1/bookings directly will only receive rows where customer_id matches their UID. There is no way to read other users' data unless the RLS policy itself has a bug.

🚀 Scalability & Performance
Q26How would FUSION scale to 100,000 concurrent users?
(1) Frontend — Vite builds a static CDN-deployable SPA (Vercel/Netlify edge network handles infinite horizontal scale). (2) Backend — Node.js Express is stateless; horizontal scaling behind a load balancer (e.g., AWS ALB + ECS) with no shared memory required. (3) Database — Supabase supports read replicas for horizontal read scaling. Key DB indexes on customer_id, worker_id, status, created_at keep queries O(log n). (4) Realtime — Supabase channels use connection pooling via PgBouncer. Connection limits can be raised with Supabase Pro.
Q27What performance optimizations are implemented in the frontend?
Six optimizations: (1) Route-based code splitting — each role's dashboard is a lazy-loaded chunk, so customers don't download worker code. (2) Component-level memoization with React.memo on expensive list components. (3) Virtual scrolling on long worker/service lists. (4) Image lazy loading with loading="lazy" on service and worker profile images. (5) Supabase query optimization using .select('id,name,rating') — column-specific fetches instead of *. (6) Debounced search (300ms) on service search input to avoid excessive API calls.
💡 Innovation & Future Scope
Q28What is the most innovative technical feature of FUSION?
The Cooperative Escrow + Welfare Feedback Loop is the core innovation. Unlike any existing platform: when a booking completes, the DB atomically (1) releases 90% to the worker, (2) credits 10% to the welfare pool balance, and (3) notifies the worker of both their payout and the welfare fund growth. Workers see their direct contribution to their own safety net with every completed job — creating a virtuous cycle where more jobs = stronger community protection. This is implemented as an atomic Supabase transaction, not an eventual-consistency async process.
Q29What are the future roadmap features planned for FUSION?
Phase 2 (3–6 months): UPI/Razorpay live payment gateway integration replacing the simulated escrow. Worker GPS real-time location sharing during dispatch stage using Supabase Realtime. Phase 3 (6–12 months): AI-powered worker-job matching using skill embeddings and historical success rates. Multi-language support (Hindi, Gujarati, Tamil) for worker interface. Phase 4 (12+ months): Worker-owned cooperative DAO governance using blockchain voting for welfare fund allocations. Skill certification NFTs for verified trade competencies. ONDC integration for government procurement of artisan services.
Q30If you had to rebuild FUSION in 48 hours for a hackathon, what would be the minimum viable stack?
The true MVP would be: React + Vite + TypeScript (same frontend — non-negotiable for type safety), Supabase only (drop the Express backend — use Supabase Edge Functions for the few privileged operations), Tailwind CSS (fastest way to get premium UI), and Leaflet + Nominatim (free maps with reverse geocoding). The cooperative payment model, 3-role auth, and RLS policies would still be implemented identically. The backend Express layer would only be added when privileged service_role operations exceed what Edge Functions can handle — typically at scale beyond prototype stage.
